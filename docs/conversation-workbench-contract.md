# 会话工作台体验契约 v1

目标：把首页重构为简洁、响应式的会话工作台，统一普通聊天、专业咨询、直接提交和历史恢复入口，
但不复制或冒充 Codex 品牌资产，也不改变既有 Agent、提案、HMAC 与工作流权限边界。

教程依据：Hello-Agents V1.0.3 第7章单 Agent 与受控工具、第9章有限上下文、第12章固定验收、
Extra09 最小闭环和失败留痕。

当前行为：文字能力集中在首页长表单中，聊天、图片、提案、知识与工作流纵向堆叠；普通聊天和咨询没有
独立入口，直接提交与历史恢复缺少工作台式导航和清晰的阶段表达。

验收条件：桌面与移动端均能从侧边栏进入普通聊天、专业咨询、直接提交和历史工单；消息流、输入框、
附件入口、加载/错误/空白状态清晰；只有满足服务端资格的咨询才出现提案步骤；所有保存与状态变更仍需人工动作。

允许修改：Vue 路由、组件、样式、前端状态组织、非破坏性的可测试 UI 辅助逻辑及验证文档。

禁止修改：Phase 1/2/3/5 冻结 Schema、模型业务写权限、HMAC 完整性、六状态机、高风险独立专业复查、
真实模型默认调用策略、依赖版本、多智能体、RAG 扩展、生产鉴权或数据库。

测试命令：`npm run build`、相关 `pytest`、`scripts/verify.ps1`、桌面与 390×844 隔离浏览器验收。

人工确认点：咨询生成提案、提案字段确认、正式保存、派工、整改、复查关闭和照片关联全部保留显式确认。

## 冻结信息架构

- 左侧主入口：`新建聊天`、`新建咨询`、`提交工单`。
- 左侧恢复入口：最近正式工单摘要及 `查看全部历史`；未保存临时会话不伪装成持久历史。
- 主体会话区：模式标题、边界说明、消息流、空白引导、输入 composer、附件/图片入口、发送状态与错误恢复。
- 受控工单区：只有咨询满足服务端 `can_propose=true`，或用户进入直接提交路径时出现；始终依次经过
  `生成待确认提案 → 核对展示字段 → 确认提案 → 保存正式草稿`。
- 正式记录详情继续显示服务端状态、revision、时间轨迹、知识依据、照片证据和人工动作。

## 会话模式

| 模式 | 入口 | 主要目的 | 工单能力 |
|---|---|---|---|
| 普通聊天 | `/chat` | 一般问答与安全知识表达 | 不展示生成/提交工单步骤 |
| 专业咨询 | `/consult` | 信息提取、追问、风险判断 | 仅服务端 `can_propose=true` 后展示生成提案 |
| 直接提交 | `/submit` | 结构化补齐四类问题 | 可生成提案，但仍须确认和保存 |
| 历史工单 | `/records`、`/records/:id` | 恢复唯一状态源并继续人工流程 | 只使用既有服务端动作 |

普通聊天和专业咨询复用同一文字 API 与会话界面，但请求携带服务端校验的intent：普通聊天走轻量模型
直答且永不调用提案接口；专业咨询走结构化风险分析并显示后续工单资格。两种intent不能共用会话；
模式切换取消当前等待并开始新的临时问题，不把不同目的的上下文混在一起。

## 状态迁移与工单出现条件

```text
空白 → 发送中 → 已回复 →（继续追问 | 新建会话）
                       └─ 专业咨询且服务端 can_propose=true
                          → 可生成提案 → 提案待核对 → 已确认待保存 → 正式 draft
                          → submitted → assigned → rectifying → pending_review → closed
```

- 发送失败回到可编辑状态，保留输入与同一幂等请求，不自动重试。
- 点击发送后，用户消息立即进入消息区且composer清空；模型等待可取消，文字分析不阻止切换到其他入口。
- 有未发送补充时禁止使用旧分析生成提案；提案成功后原咨询冻结。
- `consultation/unknown`、信息不足或普通聊天均不出现生成工单按钮。
- 高风险跨轮保留；前端不能降低风险、取消人工复核或绕过独立专业关闭规则。
- 直接提交只构造既有严格 `IssueAnalysis` 预览，不直接创建记录；HMAC、确认失效、幂等保存规则不变。

## 冻结浏览器验收场景

- W01 桌面空白页：四类入口、侧栏最近工单、清晰空白引导与 composer 可见。
- W02 普通聊天：可发送/追问，永不显示生成工单动作，附件入口可发现。
- W03 专业咨询追问：信息不足时显示追问；补充后服务端允许时才出现生成提案。
- W04 高风险：立即避险与人工复核突出，后续低风险文字不能降级。
- W05 工单链：生成提案、修改字段、确认失效、重新确认、保存草稿均清晰且防重复提交。
- W06 直接提交：结构化入口可达，仍经过提案/确认/HMAC/保存，不直接落库。
- W07 历史恢复：最近记录、全部列表、详情刷新和人工工作流可继续。
- W08 状态反馈：文字、历史、详情、提案分别覆盖加载、空、错误和成功；重复点击受禁用保护。
- W09 图片入口：composer 可发现图片能力；上传、外发分析和照片关联仍遵守原授权与阶段规则。
- W10 移动端：390×844 无横向溢出，侧栏可开合，composer 和主要动作可键盘操作。

真实文字与图片模型调用为 0；浏览器验收使用隔离 Store 和 Fake/Mock 服务。

## 极简消息与普通聊天提示词修订（2026-08-30）

目标：消息区接近用户给出的 Codex 参考，无消息头像，用户消息靠右，助手正文简洁，步骤默认折叠。
教程依据：第7章最小对话、第9章可信上下文、第12章可复现评估、Extra09真实执行状态。
当前行为：用户消息靠左；每轮显示头像、助手名称与轮数；普通聊天系统提示词自称“中文日常问答助手”，
上轮回答又作为上下文带入；系统未提供当前配置的模型标识，存在重复介绍和型号猜测的诱因。
验收条件：

- M01 已发送和等待中的用户消息均靠右，助手靠左；不显示消息头像、助手名称或轮数。
- M02 每条已完成回复仅显示可展开的“用时 N 秒”；展开后可查实际阶段、工具与 Mock 标识。
- M03 等待时仍显示经过秒数、当前服务端阶段及真实工具名；不以计时器编造工作步骤。
- M04 普通聊天提示词集中为 `agents/text_assistant.py::CHAT_SYSTEM_PROMPT`；只在被问身份时简短介绍，
  不重复角色/内部规则；型号仅依据服务端当前配置标识，不自称最新版，不向普通问题主动报型号。
- M05 Fake SDK核对真实调用边界中的system消息、模型标识、日期和不可信历史分层；不把Fake回答当作
  模型遵循提示词的效果证据；保留10秒超时、零重试、长度校验及无工具调用。
- M06 桌面和390×844布局无横向溢出，发送即显/错误恢复/风险提示/人工确认均不回退。

允许修改：TextPanel及相关样式、普通聊天系统提示词、对应测试、编辑指南和验证记录。
禁止修改：专业咨询JSON提示词及Schema、业务状态/人工确认、图片授权、模型配置与密钥、依赖版本。
测试命令：相关pytest、`npm test --prefix frontend`、`scripts/verify.ps1`、隔离Fake Chrome DevTools验收。
人工确认点：真实模型的重复介绍改善与型号回答仍需另行实际抽样；本次不调用收费模型、不自动合并PR。
