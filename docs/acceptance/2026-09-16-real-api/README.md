## 3. 主要问题与复现

### F01 · P1 · 未检索却声称已检索，虚构来源编号

新建会话、快速回复、开启工具，发送：

> 地区为中国大陆。请使用本地知识检索查施工现场消防通道管理的一般依据，说明来源及适用范围。这是一般咨询，没有具体现场事件。

**预期：** 实际调用 `search_knowledge`；引用只能对应工具返回资料。没有检索时不得声称“来自本地已核验目录”。

**实际：** `tool_results=[]`、`sources=[]`，但正文声称已经检索，列出 `[S1]`、`[S2]`、`[S3]`，并输出车道宽度和间距等具体数字。此处只记录模型生成了这些数字，不认可其工程适用性或准确性。API 将其作为 validated 结果保存，页面没有来源真实性警告。

**归因：** 模型本次未遵从工具要求；产品仅以 Prompt 约束真实性，未将回答引用与实际工具证据绑定。这是产品验收失败，不能因为 JSON Schema 合格而算作成功。模型存在随机性，不声称每次都复现。

**对照：** 新会话明确要求“实际调用 search_knowledge”，确实得到 1 条真实候选依据 KB-SAF-031（条目明确不提供具体通道宽度），返回 1 个可核查来源。说明工具可执行，但工具选择和回答约束不可靠；对照成功不撤销原失败。

**建议：** 对来源编号和证据声明增加与本轮实际结果的确定性校验；无依据不能包装成检索结果。还需解决生成期间未核实断言直接流向界面的策略，不能只在最终结果增加一条免责声明。

证据：[knowledge.json](knowledge.json)、[knowledge-repeat.json](knowledge-repeat.json)、[移动端截图](mobile-false-sources.jpg)。

### F02 · P1 · 多轮简短回答脱离 JSON 契约，正常问题整轮失败

复现：先问“用两句话解释什么是人工智能”，再问“把你刚才的解释改成一句话”，关闭工具后问：

> 换个问题：请写一句祝朋友生日快乐的话，不要提上一个话题。

**预期：** 回答最新问题，不重复历史，不报协议错误。

**实际：** 首次 1.734 秒、复测 1.375 秒均返回流内 `invalid_text_output / 回答为空或超出容量上限`，0 段正文。复测 SDK 返回 `finish_reason=stop`，有内容和 usage，但内容不是有效 JSON；不是 401、超时或空网络响应。无工具的新会话生日祝福正常，不能概括为“关闭工具必坏”。

另输入 11,738 字合成资料，首轮回答“已记住”成功；追问“只回答上述资料的最终代号”也以同类格式错误失败（1.235 秒）。长输入接收通过，不代表长上下文召回通过。

**定位：** `agents/text_assistant.py:344–346` 将历史 assistant 作为纯 answer 文本加入消息，而当前回合需要完整 JSON。模型历史格式与当前结构化要求不一致是待验证的主要原因，尚未做修复后的因果对照，不能写成已确认根因。错误提示也未区分格式失败和真正空回答。

**建议：** 统一历史消息与当前响应的协议表达，或明确隔离自然正文与辅助分析；保留严格业务校验，禁止把不合格业务数据直接落库。增加上述真实触发形态的离线回归与有限真实复测。

证据：[topic-switch.json](topic-switch.json)、[no-tools-followup.json](no-tools-followup.json)、[no-tools-fresh.json](no-tools-fresh.json)、[long-context.json](long-context.json)、[long-reference.json](long-reference.json)。

### F03 · P1 · 点击新建聊天后，成功回答被界面清空

复现：点击页面“新建聊天”（进入 `/chat?new=<时间戳>`），发送“请回复：测试完成。”并等待成功。

**实际：** 地址变为 `/chat?chat=TXT-8e5ec54a098747769a33b8c66038dd63`，服务端已有 1 轮且 answer 为“测试完成。”；页面却显示“新建聊天 / 你好，今天想聊点什么？”，消息区为空。刷新后能够恢复。停止后刷新、再手动重试成功的路径也发生同样清屏。

**定位：** `HomeView.vue:38` 在成功后将查询参数从 `new` 换成 `chat`；`TextPanel.vue:149` 对 `newChatKey` 的任何变化都执行 reset，并递增 restoreGeneration，使恢复失效。需要区分主动新建与成功绑定会话，不能对 `new→空` 无条件清空。

**建议：** 只在显式新建请求时重置；增加真实路由 `new→chat` 的组件集成回归。现有 43 项前端测试全部通过但未阻止该缺陷。

证据：[new-chat-repro.txt](new-chat-repro.txt)、[retry-ui-empty.txt](retry-ui-empty.txt)。两份证据均包含同一时刻 DOM 与服务器已保存数据对照。未观察到实际丢失服务器记录。

### F04 · P2 · 普通跟进问题持续追问，无法顺畅进入申请

四类合成现场问题均正确分类。安全紧急案例 `can_propose=true`；后勤、质量、管理案例虽然明确要求跟进，均返回 `collect_more_info`、`can_propose=false`。

后勤案例已提供项目、房间、持续时间、无人身危险；按追问再补齐设备类型与编号、具体症状、是否已报修、是否共性故障，并明确要求“生成申请供我人工确认保存”。实际仍只给一段文本建议稿，继续要求渠道、期望时间、保修等信息，没有工单申请入口。维修诊断本可留给人工现场核查。

**归因与限制：** 这是本轮真实模型的路由表现，后端忠实执行所选路由；未证明每个不完整描述都应直接申请。当前契约没有清楚区分“足以创建待核查申请的最低信息”和“完成维修判断的信息”，需要产品规则澄清并加强固定案例约束，不宜用放宽所有权限来修复。

**建议：** 明确最小申请字段；让“诊断未知”与“无法创建待核查申请”分离，保存、派工和关闭继续保留人工门禁。先覆盖本报告的后勤两轮案例，避免无限补充。

证据：[logistics.json](logistics.json)、[logistics-complete.json](logistics-complete.json)、[quality.json](quality.json)、[management.json](management.json)。

### 其他观察

- 问候主动介绍“海之子助手”，且问候、改写、一次简短计算出现辅助分析不可用提示。正文保留、无旧工单资格继承符合降级设计，但普通聊天体验仍受影响。初次未记录原始不合格分析字段，不能猜测具体哪个字段导致降级。
- 9月16日控制台一条 404 对应 `/favicon.ico`；业务 JS、CSS、聊天 API 均 200。这是低优先级资源缺失，不是聊天失败根因。
- 紧急案例用户问“可以自行关闭吗”，模型将其理解成关闭配电箱的危险操作；代码最终强制保留高风险提示。存在语义歧义，不能凭此断言模型正确理解了工单关闭，但禁止自行解除风险的确定性门禁通过。
